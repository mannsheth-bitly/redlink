# Non-Functional Requirements

## 1. Performance

### Requirement

Matching a request against **10,000 donors** must finish in **under 1 second** (spec Section 16).

### Measurement

`npm run bench` ([`server/src/bench-matching.ts`](../server/src/bench-matching.ts)):

- inserts 10,000 synthetic donors spread over a 60 km radius around Mumbai, with a realistic blood-group mix, 85% available, 20% recently donated and 30% verified;
- times each case 7 times;
- runs in a separate `_bench` database that it drops afterwards.

Measured on the development laptop (Windows 11, Node.js 24.20, MongoDB 9.0.2 running locally) on 14 Oct 2026:

| Case | Bounding box + Haversine (median) | No prefilter, all 10k donors (median) |
|---|---|---|
| NORMAL, 10 km, B+ | **7.3 ms** | 87.8 ms |
| URGENT, 25 km, O+ | **21.1 ms** | 63.9 ms |
| CRITICAL, 50 km, AB+ (all 8 groups compatible) | **79.2 ms** | 105.9 ms |
| CRITICAL escalated, 100 km, AB+ | **99.1 ms** | 107.1 ms |
| **Full broadcast**, URGENT 25 km: match + save 50 matches + 50 notifications in one transaction | **47.0 ms** | — |

Worst single run across all cases: 154.5 ms. **Every case is well under the 1-second target.**

The prefilter matters most for the common small-radius requests: 12× faster at 10 km, 3× at 25 km. At 100 km the box covers almost the whole synthetic city, so it filters little. That is expected, and it is also the rare case: only a CRITICAL request that has already escalated searches 100 km.

### Other performance measures in the design

- Indexes on every frequent query (see [ER_DIAGRAM.md](ER_DIAGRAM.md)), including `{ role, status, lat, lng }` for the prefilter.
- Each page is a separate JavaScript chunk loaded on first visit. The map (Leaflet) and charts (Recharts) load only on the pages that use them.
- Lists keep their previous data while refreshing, so polling doesn't make them flash or jump.
- Notifications are polled every 10 s, or 5 s while an urgent alert is unread. Each poll is one small JSON response.

## 2. Security

| Threat | Measure |
|---|---|
| Stolen password database | Passwords hashed with **bcrypt** (10 rounds, per-password salt). The hash is never sent to the browser (tested). |
| Session theft by script (XSS) | Session is a **JWT in an httpOnly cookie**, which JavaScript can't read. `SameSite=Lax`; `Secure` in production. Signed with HS256 and a secret from the environment. |
| Cross-site request forgery | `SameSite=Lax` cookies: browsers don't attach them to POST / PATCH requests from other sites, so another site can't act as a logged-in user. The API also reads JSON bodies only. |
| Using another role's features | **Role guards on every API route** (`requireUser([...roles])`), mirrored by route guards in the React app. Resources are also checked for ownership: you can only view or act on your own requests (or as the chosen hospital), your own matches, your own contact requests. |
| Suspended / unverified accounts | The user is **reloaded from the database on every request**, so approval and suspension take effect immediately, even for sessions that are already open. Pending, rejected and suspended accounts get 403 on everything except their status screen. |
| Invalid or malicious input | Every request body and query string is validated with **zod**. Invalid ids give 404, not a crash. Strict query filters in Mongoose. Admin search escapes regular-expression characters. Email HTML escapes user text. |
| Password guessing / sign-up spam | 10 wrong passwords per email + IP in 15 min → 429 with a wait message. In production, 20 sign-ups per IP per hour. The same error is shown for an unknown email and a wrong password, so email addresses can't be probed. |
| Race conditions (double-counting units, double escalation) | MongoDB **transactions** + **conditional updates**. Unique index on (request, donor) for matches. |
| Vulnerable dependencies | `npm audit` reports 0 known vulnerabilities (14 Oct 2026). The shadcn code-generator package was removed; its one CSS file is copied into the project. |
| Leaking secrets | `.env` is git-ignored; `.env.example` holds placeholders only. In production the JWT secret is generated by the host. |

## 3. Privacy

Donor data is protected **by default**, and only the server decides what each viewer may see:

| Data | Who sees it, and when |
|---|---|
| Donor's exact location | **Nobody else, ever.** Distances are rounded to 0.5 km ("~3.5 km", "< 0.5 km"). Map pins on the search page are snapped to a ~1 km grid, and donors in the same square share one pin. |
| Donor's full name | Masked ("Rahul S.") in search results and on request pages until the donor **accepts**. |
| Donor's phone number | Only to the requester or chosen hospital after the donor **accepts that request**, or to a receiver after the donor **accepts their contact request**. The acceptance tests check the raw API responses: the phone never reaches the browser before that. |
| Receiver's phone | Only to the donor, after the donor accepts the contact request. |
| Hospital address | Shown to a donor only after they accept. Before that, only the hospital name and distance. |
| Who reported whom | Reports go to admins only. The reported person is not told who reported them. |
| Demo data | All people, phone numbers and organisations in the seed are fictional. Phones use the `90000xxxxx` block; emails use reserved domains (`.test`, `example.com`) that never receive mail. |

## 4. Usability and accessibility

- **Mobile-first.** Every page was checked at 375 px wide, in light and dark mode, with no sideways scrolling. An automated sweep covers 38 pages in each mode.
- **Dark mode.** Follows the system setting, with a toggle. Dropdowns and charts are readable in both themes.
- **Installable** on phones (PWA manifest, home-screen icons). Chrome reports it as installable.
- **Accessible.**
  - Form fields have labels.
  - Dialogs and tabs work with the keyboard.
  - Buttons that act on a person say who (e.g. "Suspend Neha Singh").
  - Charts have text alternatives.
  - Colour is never the only signal: urgency badges and statuses also carry text, and CRITICAL also pulses (not when "reduce motion" is set).
- **Feedback.** Every page has a loading skeleton, an empty state and an error state with "Try again". Every action shows a toast. A page that fails to load shows "Reload" instead of a blank screen.

## 5. Reliability and availability

- Multi-document actions are **atomic** (transactions). Emails are sent only after the transaction commits.
- Background rules (expiry, CRITICAL escalation) run **lazily and idempotently**. A server restart loses nothing, because there is no in-memory job queue.
- `GET /api/health` reports whether the database is reachable. The hosting platform uses it to restart the service if needed.
- Works **offline** on a local network for demonstrations. If map tiles or address search can't load, the page says so and everything else keeps working.

## 6. Maintainability

- Domain rules are **pure functions** in one shared package, covered by **187 unit tests**.
- **Acceptance suites** cover every phase:
  - the API checks in `tests/acceptance/api` (`npm run test:api`);
  - the browser checks in `tests/acceptance/ui` (`npm run test:ui`).
- Strict TypeScript across all three workspaces; the build fails on any type error. Lint reports 0 warnings.
- Constants (radii, scores, cooldown, limits) live in `shared/src/domain/constants.ts`.
- Decisions and their reasons are recorded in [DECISIONS.md](DECISIONS.md).

## 7. Scalability

The current design comfortably handles a city (measured above: 10,000 donors in milliseconds). For a state or national rollout, this is the path:

| Bottleneck | Next step (MongoDB-based) |
|---|---|
| Geographic search over millions of donors | Store location as GeoJSON with a **`2dsphere` index**. Replace the bounding box + Haversine with MongoDB's `$geoNear` / `$geoWithin` (`$centerSphere`), which return donors already sorted by distance from the index. |
| Database size and traffic | **MongoDB Atlas**: replica set for failover and read scaling. **Sharding** by region (e.g. state or pincode prefix), since requests are local by nature. |
| Sending many notifications | Move notification sending out of the request to a **job queue** (e.g. BullMQ on Redis, or Atlas Triggers), with retries for email / SMS. |
| Polling load (every user every 10 s) | Replace polling with **WebSockets** or Server-Sent Events, so the server pushes alerts only when something changes. Add web push for closed tabs. |
| Lazy escalation / expiry | Move to a **scheduled worker** (cron or a queue's delayed jobs), so timing doesn't depend on users polling. |
| Single API server | Run several stateless API instances behind a load balancer. Sessions are JWTs, so no shared session store is needed. Move the in-memory login-attempt counter to Redis. |
| Map tiles and geocoding at volume | Self-hosted tile server / geocoder, or a paid provider within its usage terms |
